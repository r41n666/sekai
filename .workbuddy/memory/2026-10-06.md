### 关键坑（已写进代码注释 + README known limitations）
1. `trim` 用**导入后的网格本地坐标**——glTF 导入器把 Sketchfab 的 ×100 缩放/换轴烘进了顶点，与文件原始数字差一个缩放+换轴。
2. `ArrayMesh.get_aabb()` 在网格重建后**不刷新**，核对包围盒必须用 `get_faces()` 自己算。
3. headless 下刚 `add_child` 的节点 `global_transform` 还是单位阵，工具采样要沿父链累积**本地**变换。
4. GDScript `Transform3D(轴,轴,轴,原点)` 与 `.tscn` 的 `Transform3D(12 floats)` 互为转置。

### 趴下姿态（原来仰面朝天、头朝后、悬空）
- `player._update_stance()`：`_model.rotation.x` 由 `-1.45`（≈ -83°）改为 `PI*0.5`（+90°）
  → 正面 +Z 转到 -Y（脸朝下）、头顶转到 +Z（头朝前）= 向前趴下、正面朝下。
- 贴地：新增 `MikuModel.ground_gap()`（同帧手动沿父链累乘局部变换，量当前最低点相对玩家原点的高度差），
  `_update_stance` 每帧 `_model.position.y -= ground_gap()`（**闭环**，一步到位不抖）。实测两模型 gap=0.000。

### 关键坑（本轮踩到的）
1. **测试相机要跟模型自己的坐标系走**：`main.tscn` 里 player 根相对世界转过 180°，写死世界坐标 `(0,0.95,+1.9)` 其实摆到模型背后，
   一度误判「朝向反了」。正确：用 `MikuModel.global_transform.basis.z`（= 角色正前 +Z）算机位。
2. **同帧读不了 `mesh.global_transform`**（父节点改完变换后子节点当帧未刷新）→ 量包围盒必须手动累乘 `.transform`。
3. **闭环优于预测**：一次测量算「该抬多高」会输给程序化姿态/骨骼/各模型嵌套偏移。
4. **headless 模式下 `RenderingServer.frame_post_draw` 会卡死**，离屏截图必须用**窗口模式**（`godot --path . res://xxx.tscn`，不要 `--headless`）。

#### 任务 B：待机微动作（新文件 `scripts/entities/miku_idle_motion.gd`）
- **只在 `MikuModel` 与载入模型之间插一层 `IdleMotion` 节点**，微动作用在该层 →
  和 `player.gd` 写 `MikuModel` 的站/蹲/趴姿态（rot/pos）**物理隔离**，互不打架。
- 三层正弦：① 呼吸（Y 升沉 + 极轻微整体缩放脉动）② 重心微移（X 左右 + Z 前后，小椭圆）③ 上身摆动（Y/Z/X 转动）。
- **无循环接缝的原理**：三频取**互不成整数比**（默认 0.24/0.14/0.18 Hz）→ 合成波长极长；每通道叠二次谐波。全正弦驱动 = C1 连续。
  数值实测：60 fps 相邻帧最大跳变 `0.0007 m` / `0.0011 rad`；扫过 60 s 相位的二阶差分峰值 **3.6e-5**（≈ 无断裂）。
- **趴下自动淡出**：`MikuModel._process` 按**世界「上方向」**判定倾斜（不依赖调用方，player.gd / bot.gd 通用），
  指数平滑把 `intensity` 从 1 拉到 0。实测站立 1.000 / 平躺 0.000。
- **调参位置**（`miku_model.gd` 顶部两张表，键 = 模型目录名）：
  `DEFAULT_IDLE_PROFILE`（默认，轻微，避免盖过自带动画）+ `IDLE_PROFILES`（目前只给 `miku_statue` 调了一组：呼吸更沉、摆动更明显）。
  参数含义（幅度 = 米/弧度/比例，频率 = Hz）在 `miku_idle_motion.gd` 顶部注释。
- 实测幅度与配置吻合：`miku_statue` 位置 `x±0.052 y±0.039 z±0.028 m`、旋转 `y±0.096 rad`；其余约 0.5×。
- 离屏实拍 `miku_statue` 四个相位（0/1.25/2.5/3.75 s）：重心左→右→中→左摆动弧 + 头部偏转 + 双马尾跟随，四点无破面、脚不离地。

#### 关键坑（本轮踩到的）
1. **离屏取景用的包围盒必须排除道具** —— 先用「全部网格」包围盒摆相机，`miku_classic` 的展示台把包围盒撑到跨 10.9 单位、
   中点偏出角色，相机几乎贴地侧看 → 一度**误判「模型躺平了」**。改用**骨骼包围盒**取景后立刻是正常站姿。
   结论：几何异常先怀疑测量，再怀疑模型。
2. **`--check-only` 不解析 `class_name`** —— 单脚本检查会报「找不到 MikuIdleMotion」，必须先跑一次全项目 `--import`
   建立全局类缓存，之后的检查才可信。
3. **`queue_free()` 帧末才释放** —— 展示台要在量包围盒前真正消失 → 用 `remove_child()` + `free()`（先 detach 再 free）。
4. **探针别复用同一个 `MikuModel` 节点多轮测试** —— `_ready()` 会用默认路径自动 `load_model()` 一次，
   再手动调一次 = 加载两遍，打印混进上一轮残留、读数全错。改成每轮新建节点 + `model_path` 指向不存在的路径。
5. `global_transform.basis.orthonormalized().y.y` 是判断「立/躺」的干净量（1 = 直立，0 = 平躺）。

### 🟥 关键发现：`friendly` 组是双重语义（主理人逐行核验，**永久性工程事实**）

`friendly` 组**同时是「伤害路由键」和「阵营显示键」**，两者语义不同：

| 位置 | 用途 |
| --- | --- |
| `player.gd:138` | `_setup_remote_player()` → `add_to_group("friendly")`（注释写「当作队友显示」） |
| `weapon.gd:353` | `if collider.is_in_group("friendly")` → `apply_network_damage.rpc_id(authority)`；**否则**走 `apply_damage_to_target.rpc()` **广播** |
| `knife.gd:100` | 同样的分支 |
| `minimap.gd:20` | `ally_group := "friendly"` + `ally_color` 绿 → 画绿点 |
| `teammate_icons.gd:48` | 遍历 `friendly` 画队友图标 |

**语义真相**：`friendly` 实际含义是「**这是个远端玩家**」（所以要路由到他的 authority 而非广播），
UI 层却读成「**这是个盟友**」。团队模式下两者恰好重合；**MVP = FFA 个人死斗下彻底背离** —— 会显示成「绿点友军 + 可击杀」。

⚠ **陷阱**：只把远端玩家移出 `friendly` 修显示 → `weapon.gd:353` / `knife.gd:100` 掉进 `else` 分支 →
伤害从「只发被击中者 authority」变成**广播到所有端** → **联机伤害直接坏掉**。
**结论：显示改动必须与伤害路由解耦一起做。**

**正解**：解耦「身份」与「阵营」——路由改用中性判据（`collider.has_method("apply_network_damage")` 或新增 `remote_player` 组），
显示层另设阵营组。验收条款 **AC-A3b**：联机下 A 击中 B → 伤害只发 B 的 authority、未落广播分支。
已派 engineering-lead 写进「组契约表」+ 新增一条 ADR（「组作为隐式接口」反模式）+ 加「改动前置检查：改组归属必须 grep 全部 `is_in_group` 消费点」。

## 🔴 C-18：联机击杀归因断裂（第二次 G4 实测暴露，比分恒为 0）

### 现象（用户第二次双端实测，peer=540319056）
两端**扣血与阵亡全对**（`player_health_changed hp=75→50→25→0` + `player_died` 反复出现），
但 `score_changed scores={1:{kills:0,deaths:0}, 540319056:{kills:0,deaths:0}}` **从头到尾不变**。
用户实际在互射、也在阵亡重生 —— 所以不是「没打到人」，是**打到了但没计分**。

### 根因（一行）
`weapon.gd::_deal_damage()` 用**射手端本地**的 `collider.health` 判生死：
`var killed := hp_before - damage <= 0.0`。
远程玩家的血量**只在受害端结算**（`apply_network_damage` 是 `call_remote`，**血量不回传射手端**）
→ 射手端对方血量**恒为满值 100** → `100-25<=0` **恒假** → `killed` 恒假
→ `_report_kill_if_player()` **从不执行** → 比分恒 0、15 杀永不 `match_ended`。
- bot / 训练靶**不受影响**：走 `apply_damage_to_target.rpc` 广播、各端都结算 → 各端血量一致。
- `knife.gd` **同一处缺陷**（已同口径修复）。

### 修复 `6878539`（权威端判定 + 回传确认，**A.4 契约不变**）
- `player.gd::apply_network_damage(amount, shooter_peer_id: int)` —— 第二形参从只读展示的 `_shooter: String` 改为 `int` peer id。
  本端是**全场唯一知道血量真值的地方** → 归零时 `net_confirm_kill.rpc_id(射手)`。
- `player.gd::net_confirm_kill()`（`@rpc("authority","call_remote","reliable")`）在射手端收到确认后
  → `_report_local_kill()`（复用 A.4 既有「权威端直调 / 客户端 `rpc_id(1,…)`」两条路径）。
- **`was_alive` 守卫**：`var was_alive := health > 0.0` 必须在 `take_damage` **之前**求值（取挨枪前血量），
  保证一个死亡周期只回传一次 → 不重复计分。
- **为何绕一跳**而非让受害端直接找房主上报：A.4 语义是「**击杀者**上报、房主用 `get_remote_sender_id()`
  反查击杀者」；若受害端上报，房主会把 sender 当成击杀者 → **归因反成「受害者是击杀者」**。

### 为什么这个缺陷能连跑两轮 G4 都没被发现（真正的元问题）
观测层只接了 `ScoreManager` 的 4 条信号 + 玩家 `health_changed`/`died`，
**完全没接击杀上报链路** → 「扣血正常但比分恒 0」在日志里**没有任何可见痕迹**，
看起来就像「打不到人」。已补：`player.gd` 新增 `remote_kill_confirmed` 信号 + 观测层打印 `kill_confirmed`。
读法：有 `kill_confirmed` 且比分 +1 → 通✔；有确认但比分不动 → 断在 ScoreManager；无确认 → 命中判定问题。

### 回归基线
`tests/suites/test_kill_attribution.gd`（9 用例）+ `test_runner.gd` 登记（**登记是手写的 `SUITE_SCRIPTS` 数组，不自动发现**——新 suite 漏登记会静默不跑，我第一次就踩了）。
verify **67/213 → 75/231/0** PASS。
- ⚠️ **`was_alive` 用例必须断言「求值顺序」而非「token 存在」**：我先写成 `body.find("was_alive") >= 0`，
  用变异测试（把 `was_alive` 改成恒 `false`）验证 → **仍然全绿，断言是假的**；改为断言

### 本轮踩到的四个坑（都已转成清单条目 / 工具护栏）

① **纪律锁用字面量搜源码 = 两个缺陷同时存在**（已写进 `control_checklist §4-13`）：
   - **(a) 搜到自己的注释**：注释里写「不得出现 `kills >`」→ 字面量锁命中自己 → 用例无端转红。
     **最危险的后续动作**：有人为了「让用例变绿」去删注释 = 把纪律说明也删了。
     → 纪律锁必须**先剥注释**。
   - **(b) 换个写法就绕过**：M3 变异体用 `get("kills", 0) > 0` 绕过了 `find("kills >")`，
     **首轮存活**。→ 必须按**语义**锁（字段 × 运算符组合枚举：「代码中不得出现
     `kills`/`deaths` 的任意比较运算」+「`winner_id` 形参不得被赋值」）。
   - 剥注释时**只能保留 `#` 之前的代码**，不能「有 `#` 就整行丢」——
     否则 `xxx(true) # 注释` 的代码部分也被丢掉，代码明明在却报「没调用」（我真踩到了）。

② **变异脚本必须校验注入是否真的生效**：M3 首轮「存活」实际是**锚点不匹配、什么都没注入**
   —— 工具缺陷被误报成测试缺陷，差点去重写一条本来正确的断言。
   同理**注入失败必须让脚本非零退出**：中途改写脚本时出现过「7 个变异体全部注入失败」
   却打印 **"MUTATION PASS"** 的假绿。**「全绿结论」比「红结论」危险得多。**

③ **实测探针不要改`main.tscn`**：ES-4.1 的做法是「临时往 `main.tscn` 挂节点、跑完删干净」，
   那个清理动作本身就有风险（同 §4-11：清理不干净就会把改动留在场景文件里）。
   本轮改为**探针自带独立场景**，完全不碰 `main.tscn` → **收尾零残留**，无需清理。

④ **`.uid` 伴随文件**：`git status` 里的 `?? xxx.gd.uid` 必须一并入库（Godot 4.4+ 用uid
   引用资源，漏提交 → 别人拉取后 uid 失配 → 场景加载失败，而本地因缓存看不出来）。
   → 已写进 `control_checklist §4-14`。

## D2-04 规则配置化与玩家属性（engineering-lead · 程基岩）

### 落地了什么
`scripts/game/rules/` 8 文件 + `tests/suites/test_rule_config.gd`（59 用例 / 308 断言）
+ `tools/mutation_rule_config.py`（6 杀 + 3 守恒）+ `tests/manual_rule_config_probe.tscn`
+ `ADR-009-rule-config.md`。回归基线 **185/716/0 → 244/1024/0**。

### 值得固化到肌肉记忆的三条

**① 「不可用」必须显式，且要推到三层。**
本项目用户点名的 5 种条件里 3 种（回合/道具/Boss）**无任何支撑系统**。
返回 `false` 会让「配了 5 个只跑通 1 个」看起来像「另外 4 个没达成」——**C-18 同源**。
故设计成三态（`OK_TRUE` / `OK_FALSE` / `UNAVAILABLE`），并把纪律推到：
- **加载期**：`validate` 拒收占位类型 → 整份回落默认（不静默接受半份配置）
- **运行期先普查后组合**：⚠️**这是最容易漏的一层** —— `ANY_OF` 下若先组合求值，
  首个条件成立就短路返回，后面的不可用条件**永远没被看见**，纪律静默失效（变异体⑥）
- **求值期纵深防御**：只翻 `judgeable` 没翻 `evaluate` 时仍按不可用处理

**② 公开可写字段是契约，不是实现细节。**
`kill_target` / `match_duration` 被既有测试直接写（`test_score_manager.gd:348` / `:329`）。
「初始化时编译一次规则集」是最优雅的写法，但会让这些测试**当场转红**。
→ 本期选择**按需重建**（每次判定 2 次字典字面量 + 2 次对象构造，几十 ns，可忽略）。
**配置化提供的是「换一个真值来源」的能力，不是「把真值来源搬进配置」。**

**③ ⛔ 第 6 次栽在弱断言上，且形态极其隐蔽。**
`test_unavailable_condition_warns_exactly_once_per_match` 断言的是 `_ruleset_warned` 标志，
而该标志在 `push_warning` **之前**置位 → **把 `push_warning(...)` 整行删掉照样全绿**。
变异体 M2 存活才暴露出来。
教训：**断言了状态 ≠ 断言了行为**。「告警了没」不能靠告警**之前**置的标志来判。
补法：源码纪律锁（剥注释后判函数体内真有 `push_warning(` 调用）+ **守恒对照 g3**
（告警文案换一种拼接写法仍须全绿）—— 否则会把正确改写误判为失败（§4-16 的「误杀」方向）。

### 顺带修掉的两个自身缺陷
- **属性规格表把 `max_health` 的 `max` 写成 `100.0`**（应为 `1000.0`）——
  被 `test_out_of_range_stats_are_clamped` 当场抓住（配 200 血被夹回 100，
  连带 5 条用例转红）。**这就是「默认值/区间必须有测试逐字比对」的价值**。
- **双端探针**：`Object.get("method_name")` 返回的是 **`Callable` 而非调用结果**
  （日志刷 `Invalid operands 'Callable' and 'int'`）→ 必须 `.call()`。
  另：等待结算那段每帧打印会把日志刷成 132 行、真正的证据反而看不见 → 改为只打首次。

### 遗留风险（已登记）
- 客户端属性补应用依赖 `main.gd::_ready()` 里 `ruleset_applied` 的连线。
  若被删掉，客户端 `max_health` 停在场景默认值 → 房主配高血时客户端**永久丢弃**血量广播。

## D2-04 · 胜负判定与角色属性配置化（用户需求第三条· 规格 + 实现）

用户要求把写死规则改为可配置、可组合。用户拍板 **Q1~Q4 全部不做**：
死亡即失败（会推翻⚑L-4 已决的「阵亡 3 秒自动重生」）、每玩家差异化血量、
真独立 score 字段、房主配置面板 UI。

### 架构：混合式（Dictionary 传输 + 规则对象求值 + 注册表扩展）
**否决 `Resource`** 的决定性理由（设计侧核对原文得出）：
`Resource` 是**引用型**对象，跨端不能按值传 → 走RPC 只能传路径字符串 →
等于把「配置一致」退化成「两端必须装同一个 .tres 且版本一致」，
**把运行时问题推给打包流程**。

采纳形态：`Dictionary` 作配置真值与传输（可 JSON/rpc/headless 构造）
→ `ConditionRegistry.compile()` 每端各编译一次成本地规则对象（**不传输**）
→ `RuleSet.evaluate(snapshot)` 纯函数求值。规则对象 `extends RefCounted`、
不碰场景树/multiplayer/时间 → 天然适配本项目既定「静态纯函数 + headless 断言」取舍。

### 防空壳三态（本次最关键的设计约束）
`EVAL_OK_TRUE(0)` / `EVAL_OK_FALSE(1)` / **`EVAL_UNAVAILABLE(2)**`
占位条件（survive_rounds / score_target / collect_items / defeat_boss）**恒返回 UNAVAILABLE**；
任一启用条件 UNAVAILABLE → **不结束对局 + 一次 push_warning**。
⚠️ 静默 `false` 会让「配了5个只跑通1个」看起来像「另外 4 个没达成」——
**形态同 C-18「比分永远 0」**（日志全正常、只有规则没生效）。
另加：`RuleSet.evaluate` **先普查不可用条件再组合求值**，
否则 `ANY_OF` 首个成立即短路 → 不可用条件永不被看见（变异体杀⑥，12 条转红）。

### 用户点名的 5 种条件实际只真跑 2 种

（`boss` grep 零结果、无独立 score 字段、无回合概念）→ 只留接口。

## 🔴 工具层缺陷（我自己踩到+ 复现两轮，已修commit `7b87bee`）

### ① 变异脚本强杀后留污染（我实测 SIGTERM 复现）
第一次跑脚本得到 **SIGTERM**，残留未写完的变异体在工作区（缩进都没对齐的语法错误）。
原因：Windows `TerminateProcess` **不给 Python 跑 `finally` 的机会**。
修复三层兜底：启动自愈（读 `PENDING.json` + 字节备份还原）+ 项目内**固定目录** `.mutation_backup/`
（不用 `mkdtemp` —— 否则强杀后找不到同一份备份）+ `atexit`& `try/finally`。

⚠️ 工程侧**自查出一个它引入的 bug**（值得记）：最初按「文件 ≠ HEAD 就还原」做自愈，
结果把**本次任务刚加的 bot.gd 注释当成残留删掉了**。HEAD 是已提交状态，而工作区允许有正在写的合法改动。
⇒ 还原目标必须是「**本次启动时的原始字节**」，且只还原本脚本**确实注入过**的文件。
这条是通用的：⚠️ **不要拿 HEAD 当"干净"的判据 —— 工作区本来就有合法的未提交改动。**

### ② `tools/verify.sh` 会删 Vulkan 锁（自我复发的伤疤）
`tools/verify.sh:129` **每次无条件**跑 `--import`，`rc==0` 直接 PASS，`run_import()` 内**零防护**
⇒ 跑一次 verify.sh 就删掉 Vulkan 锁，下一步测试转红，**失败现象指向"测试坏了"而真因是"脚本破坏了配置"**
这正是 C-19 复发 5 次却一直查不到根因的机制。

⚠️ **我的机制结论被工程侧实测反驳**：直接跑 `--import` 确实加载了编辑器布局（8 处 `loading_editor_layout`），
但 `project.godot` 事后与 HEAD **逐字节相同** ⇒ 真凶另有其人（编辑器进程/历史残留），
**「--import 必然删锁」这个因果推断不成立**。教训：我从一次相关性观察推出了因果。

**修复（且工程侧改得比我说的更严密）**：断言做成**无条件前置**而非只在 `--import` 之后。
理由（它补上了我漏的）：**锁可能在本脚本运行之前就已缺失**（上一次误用、或编辑器打开过），
若断言只在 import 之后做，类缓存已存在时的 **SKIP 路径会完全绕过检查**⇒ 正是我要防的失败模式。

**我实测验证（亲手制造第 6 次复发）**：
```
手工 sed 删掉锁 → 跑 verify.sh
⇒ FAIL Vulkan 锁缺失…已自动还原…已中止（绝不在被破坏的配置上继续跑测试）
⇒ VERIFY EXIT=1
⇒ 复核还原有效性（不信退出码，验内容）：grep 命中 1、git diff --numstat 为空
⇒ 再跑 verify：PASS 293/3372/0
```
守门真实有效，且失败现象现在**正确指向真因**。

### ⚠️ 自愈机制的一个使用边界（我实测踩到，值得记）
自愈是「还原到**本次启动时的原始字节**」而非 HEAD（这是它上一版 bug 的正确修正）。
⇒ 若上一次强杀留下的残留**在本次启动前就已存在**，脚本会**原样保留**它（它无法区分
「上次残留」与「开发中的合法改动」）——这是设计上的正确取舍，代价是**残留只能手工或git 清一次**。
我的验证场景就撞上了这点：注入残留后再跑脚本，它把残留当成了"本次启动时的基线"⇒ 残留被保留。
⇒ 正确的验证顺序是：**先跑一次有残留的脚本 → 看到自愈触发 → 再手工 git 清残留 → 再跑一次确认无残留**。
自愈机制的真正价值是「不让**结论**建立在脏源码上」（它会打印"本次测试结论基于还原后的干净源码"），
而不是替人清理工作区。
