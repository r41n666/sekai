# ADR-008 · 远程血量显示：复用 30 Hz 广播 + 受害端权威的「纯显示副本」

> **状态（Status）**：Accepted（已采纳）
> **日期**：2026-10-06 ｜ **作者**：程基岩（engineering-lead，EP-4 · Task #10）
> **关联**：`scripts/player.gd::apply_network_state` / `_apply_display_health`、
> `scripts/network/network_manager.gd::net_player_state`、`scripts/ui/enemy_health_bars.gd`、
> `design/gdd/01_core_loop.md` 附录 A.4/A.5、`docs/architecture/adr/ADR-002-network-sync-model.md`、
> `ADR-007-group-as-implicit-interface.md`、`control_checklist.md §4-9`
> **收口的缺口**：**C-18 的遗留半边**。C-18 已把「致死判定」移到受害端权威解决
> （`player.gd::apply_network_damage` 归零时 `net_confirm_kill.rpc_id(射手)`），
> 但**射手端看到的 `collider.health` 恒为初始值 100** —— 打空了血对手照样显示满血。

---

## Context（背景与问题）

联机对局里，伤害的结算与显示分离在两端：

| 端 | 血量是什么 | 现状 |
| --- | --- | --- |
| **受害端**（被打者的机器） | **唯一真值** —— `apply_network_damage` 是 `call_remote`，只在这一端结算 | 正确，实时 |
| **射手端**（开枪者的机器） | 一个从不变化陈旧副本 —— `collider.health` 恒为 100 | **缺失**，看不到对手在掉血 |

C-18 的教训是：**射手端拿本端那份副本做任何判定都会错**（当时用它判致死 → 比分恒 0）。
C-18 修好了「判定」，但**没修「显示」**：射手端仍然不知道对手还剩多少血，
于是「我明明打中了、他怎么还是满血」这类困惑无法区分「没打中」与「打中了但看不见」。

要修的正是显示，且必须**不重复 C-18 的错**。三个待决问题：

1. **走哪条通道？** 位置已经在 30 Hz 广播（`ADR-002`），是搭便车还是另开一条？
2. **血量显示态与本地权威血量的关系？** 尤其：射手端要不要因为「看到对手掉血」而扣自己的血 / 进死亡流程？
3. **显示在哪、怎么保证可读？**

## Decision（决定）

### 1. 通道：**复用已有的 `net_player_state`（不新开 RPC）

`net_player_state(pos, yaw, health)` —— 在既有的 ~30 Hz 广播里加第三个载荷，**广播次数不变**。

理由：
- **不增加广播次数 / 带宽不翻倍**。位置本来就在 30 Hz 发，血量搭同一趟车，边际成本只是每包多4 字节。
- **30 Hz 对血条绰绰有余**。人眼对「连续量平滑」的阈值远低于 30 Hz；掉血是离散跳变，30 Hz 的刷新
  比任何显示器刷新率都慢不了多少，且受伤瞬间下一包（≤33 ms）就到。
- **不动 `unreliable_ordered` 的语义**（`ADR-002`）。血量与位置同为「周期性状态广播」，
  丢一包由下一包覆盖 —— 与位置**完全同构**，不需要新的可靠性论证。
- **迟到加入天然可用**。本 ADR 沿用 `ADR-002` 的「用普通 RPC 而非场景缓存」范式：
  新加入者第一帧就同时拿到位置与血量，不需要「补发一次全量状态」的额外路径。

⚠ **代价（明写，不藏）**：
- **RPC 签名是破坏性变更**。`net_player_state` 与它转发的 `apply_network_state` **两处必须同步改成 3 参**；
  不一致不会编译报错，只在派发时炸（`rpc_id` 实参个数不匹配）。
  → 已由 `tests/suites/test_health_sync.gd::test_send_and_receive_arity_matches`（**运行时反射取元数**，
  不是数源码字符串）与 `test_rpc_call_sites_pass_three_arguments` 双重钉死。
- **首次见到某玩家时血条要等最多 1 帧**（≤33 ms）才出现。可接受（换来的是带宽不翻倍）。

### 2. 权威与边界：**受害端唯一真值；射手端只更新显示副本

- 血量真值**只在受害端**。射手端**不得**本地推算 / 扣血（那会重演 C-18 的两套口径打架）。
- 射手端把收到的值写进**独立的显示副本** `_display_health`（经 `get_display_health()` 读出），
  **不写 `health`、不调 `take_damage`**。
- **非法值（NaN / ±INF / 负数 / 超 `max_health`）整个丢弃并保持上一有效值**。
  ⚠ 故意**不是** clamp 成一个看起来合法的值：超上限只可能来自协议污染或两端配置分叉，
  此时显示一个被夹过的值 = **把 bug 伪装成合理数值**。下一包正常值自然会纠正。
  clamp 仍作为**写库前的最后一道夹取**保留（纵深防御，防止将来有人绕过守卫）。
- **显示态不驱动本地死亡流程**：不发 `died`、不调 `_enter_dead_state`、不改 `input_blocked`。
  死亡 / 重生是**受害端的权威流程**，射手端不替它决定（否则会出现「我死了但我还能动」这类穿帮）。
- **血量是纯显示态，不参与任何胜负 / 计分判定**（胜负唯一口径 = `ScoreManager._evaluate_winner`）。

### 3. 信号：**新增独立的 `remote_health_changed`，不扩 / 不复用 `health_changed`

- `health_changed` 的语义是「**本地权威**血量真值变了」，被本地 HUD 血条 / 死亡界面
  **当真值**消费。
- 把远端显示值塞进同一个信号，任何按「血量真值变了」行事的消费方就会把「显示态」
  误读成「本端结算」⇒ **C-18 的两套口径重新引入**。
- 独立信号让**来源在类型上就不可混淆**，与 A.5「不扩既有信号签名、新增独立信号」的裁定同源。

### 4. 呈现：**头顶上方世界空间血条**（`enemy_health_bars.gd`）

- **画在敌人头顶上方**，用 `_camera.unproject_position()` 做3D → 屏幕投影
  （与 `teammate_icons.gd` 同一套投影机制）。
- **故意不贴屏幕边缘**。`teammate_icons` 的贴边是**队友导航**语义（队友可能在画面外，贴边告诉你往哪看）；
  FFA 下在屏幕边缘凭空出现一条「不知道是哪个方向、哪个敌人」的血条是**误导**
  （与 `04_ux_flow §6.2`「FFA 敌我语义修正」同向）。
  → **背对摄像机 / 出画即不画**：「看得见的敌人 → 看得见的血量」，一对一映射，绝不臆造。
- **可读性按 `04_ux_flow §6` Standard 基准**（不依赖单一感官 / 颜色）：
  - **明度对比为主**：近黑底衬 + 近白填充（明度差 ≈0.9），并加一档亮的描边
    （保证在近白天空前仍有边界，对齐 AC-F4）。
  - **不只靠颜色**：填充上每 25% 一道**刻度缺口**（血量越低露出越多 —— 形状 + 位置线索）
    + 条右侧**数字读数**。低血的暖黄只是第三重冗余，不是唯一线索（对齐 AC-F3 / AC-F5）。

## Consequences（后果）

**正面**：
- **补齐 C-18 遗留半边**：射手端第一次能真实看到对手的血量与掉血过程，
  「打中没打中」不再需要靠猜。
- **带宽零增长**：广播次数不变，每包 +4 字节。
- **不新增 RPC、不新增可靠性论证**：与位置广播同构，沿用 `ADR-002` 的全部结论。
- **不产生第二套血量口径**：显示副本与权威血量在**字段层面**就分开，且各有一个 getter。

**负面 / 已接受的取舍**：
- **签名破坏性变更**：两处必须同步改（已用运行时反射测试钉死，见上）。
- **首次出现最多晚 1 帧**（≤33 ms）。
- **本端上限口径**：`get_display_max_health()` 故意返回**本端** `max_health`。
  当前两端同源于同一份 `player.tscn` 的 export 默认值（场景未覆盖）→ 跨端一致；
  若将来两端配了不同上限，显示态以**本端 UI 口径**为准（血条是本端 UI 的事，不参与任何判定）。
- **新文件 = 新增一条必须登记的测试 suite**（`control_checklist §4-9`：`SUITE_SCRIPTS` 是手写数组，
  漏登记会**静默不跑**，让人误以为「测试全绿」）。

## Alternatives considered（备选方案）

| 方案 | 为何未选 |
| --- | --- |
| **B · 新开一条独立 reliable RPC 同步血量**（如 `net_health(value)`，受害端每次扣血时发） | ① 每次受击**多发一包**（30 Hz 广播本来就有，此时两条通道并发）；② `unreliable_ordered` 与 `reliable` **混用**要额外论证顺序（同一玩家的位置与血量可能乱序到达，UI 会看到「新位置 + 旧血量」）；③ **迟到加入者拿不到历史值** —— 只有下次掉血才知道血量，而搭 30 Hz 广播的方案第一帧就有 |
| **C · 让射手端本地扣血（`apply_network_state` 里直接 `take_damage`）** | **这就是 C-18 本身**。两套血量口径 → 射手端会误判自己已死、可能触发本地死亡界面，且与受害端真值漂移。**明确否决** |
| **D · 用 `MultiplayerSynchronizer` 复制 `health` 字段** | 与 `ADR-002` 的「名单本地重建」竞争（两套生成机制）；且 Synchronizer 会把 `health` 变成**看起来像本端权威**的字段 —— 正是 C-18 的陷阱形状。**否决** |
| **E · 屏幕边缘贴边血条（复用 `teammate_icons` 的贴边逻辑）** | FFA 下语义误导（见上）。若将来上 TDM，队友血条可以复用贴边；FFA 不做 |
| **F · 不做敌方血条，只在准星命中标记里给「已命中 / 未命中」** | 用户要的是「看到对手的血量与掉血过程」，二值标记给不出程度；且实现更复杂（要额外传命中状态）却更少信息 |

## 影响 / 后续

- **回归**：`tests/suites/test_health_sync.gd`（已登记进 `test_runner.gd::SUITE_SCRIPTS`，`§4-9`）——
  RPC 元数一致 / 射手端不本地扣血 / 不触发本地死亡流程 / 非法值丢弃 / clamp /
  纪律锁（不碰计分字段）/ **30 Hz 门控未被顺手改成每帧** / 与本 ADR + `00_overview §7.2` 的文档一致。
- **变异测试**：`tools/mutation_health_sync.py`（≥4 变异体，验证断言有牙齿）。
- **`00_overview.md §7.2`** 的 RPC 清单已同步（`net_player_state` 载荷含血量）。
- **后续可能项**（不在本 Story）：受击方向的**受击指示**（被打方看到「从哪边来的」）——
  与本 ADR 的「显示态不驱动流程」口径同源，可另开 Story。
- **若将来上 TDM**：血条按阵营着色即可（`ADR-007` 的正交性保证路由不受影响）；
  本 ADR 的「受害端权威 + 独立显示副本」结论**不变**。
